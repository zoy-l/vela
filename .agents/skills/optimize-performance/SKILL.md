# 性能优化

先证明当前改动对目标负载有收益，再扩大验证。每次形成可运行的实现修改后，都重新遵循这个顺序。

## 迭代顺序

1. 明确用户指定的负载、运行模式、计时边界、统计单位和目标。优化 AOT 就测 AOT；保持本轮调查和实现围绕用户关注的执行路径。
2. 首次修改前保存可复用的基线产物或足够的来源信息。已有同口径、可核验的基线时直接复用，避免反复重建和重跑旧版本。
3. 修改实现，完成运行所需的最小构建后，**第一项执行验证必须是受影响的目标单项基准**。不要先启动全量测试、全仓库 lint、发行包验收或完整基准套件。基准自身应校验结果；构建失败、崩溃或结果错误时先修正实现，本轮不能记作性能收益。
4. 探索阶段使用足以判断方向的少量重复，尽快反馈绝对耗时、前后变化和波动。收益接近噪声时，只增加该单项的样本或进行配对测量，不提前扩大验证范围。
5. 按证据决定下一步：
   - **没有收益、退化或结果不明确**：继续检查热点、生成产物、计时边界和测量噪声，调整实现后重新测单项；不进入大范围验证。清理已经证明无用的尝试。
   - **确认有收益**：运行能发现本次具体错误的最小定向测试，覆盖结果、边界和受影响的错误行为，再继续下一项优化或进入收尾。
6. 修复验证发现的问题或继续修改实现后，先回到目标单项基准确认收益仍在，再复核受影响的测试。相关实现未变化时，不重复已经通过的验证。

## 测量约束

- 使用适合目标路径的优化构建和已有成熟基准工具。固定影响比较的输入、工作量、编译配置、预热与计时边界；双方应计算相同结果。
- 保持既定负载和安全语义。经用户授权调整负载、对照实现或语义时，分别标注结果，不能把口径变化记成原负载的优化收益。
- 测量期间不要并行运行构建、lint、大范围回归或其他重负载。多个性能基准也应避免争用资源。
- 保留全部样本并报告适合目标的统计量与波动，通常为中位数与 CV；不能挑选最好的一轮作为结论。
- 明确完整调用、循环和内核的计时范围。诊断性拆分或扣除包装得到的估算，不能混作实测调用耗时。

## 收尾与交付

1. 完成受影响生产路径，清理临时探针、失效实现和过时注释。
2. 在完成边界集中运行项目要求的相关回归、静态检查及其他必要验收。失败后只复核失败项和修复影响的范围，避免无依据重跑整套验证。
3. 验证结束后进行正式性能确认，使用足够的重复次数和必要的对照项。遵循用户要求的报告范围；单项优化不自动扩展为全套基准重跑。
4. 交付前后绝对数值、变化或倍率、波动、测量命令及验证结果，并说明实际测量范围。按项目规范保留摘要与来源，原始样本和临时日志放项目允许的位置。性能目标与正确性验证都满足后才能宣布完成；尚未达标就继续优化，或如实说明具体阻碍。
