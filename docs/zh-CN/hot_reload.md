# JIT 与热重载设计

> 状态：开发模式已接通共享原生 JIT、保留状态的 Hot Reload、重建脚本状态的 Reload，以及优化层的原版本基线恢复。H3–H5 的功能与资源生命周期已通过 Windows x64 验证，性能测量仍显示与封闭 AOT 有明显差距，见第 13 节。VM、封闭 AOT 和 VM REPL 保持各自入口。

Vela 的开发模式以及需要运行时加载源码的宿主使用 JIT，固定发布产物继续使用 AOT。两者共享前端、Typed IR、原生代码生成与运行时语义。用户可以在宿主运行期间加载或修改脚本；Hot Reload 保留脚本状态并更新后续执行，Reload 重建脚本 Isolate 并重新执行入口。**C++ binding 的实现、签名和注册集合在开发会话内固定，不参与热重载。**

本设计参考 Dart VM 的方法版本、调用更新、状态保留与原子提交语义，以及 Flutter 将代码更新和界面重建分开的做法。Vela 保留非移动 GC 和严格静态类型，不复制 Dart 的对象移动实现，也不承诺接受 Dart 能接受的全部结构修改。

JIT 与可重载能力由宿主选择，不由 C++ 的 Debug/Release 构建配置隐式决定；性能测量使用 Release 构建的 JIT。需要动态脚本的发布宿主可以包含 JIT，但必须满足目标平台的可执行内存政策，并承担编译器体积与运行时编译成本。

开发控制台使用 `vela dev app.vela`；`--optimized` 选择具有去优化恢复能力的优化层，`--code-cache=DIR` 启用可重定位目标文件缓存。控制台默认监视导入图；`.hot`、`.reload` 和 `.load FILE` 分别发起三种事务，`.status` 显示版本、阶段耗时和代码资源，`.cancel` 取消未提交请求。文件 Hot Reload 不回放交互语句；`.reset` 读取当前文件快照、移除交互历史并重建运行。`.break`、`.stack`、`.source` 和 `.continue` 使用具体版本的源码与帧。

嵌入宿主通过 [`DevelopmentSession`](../../compiler/development_session.h) 调用 `Prepare`、`Submit` 和 `Pump`，以 `Invoke` 进入当前导出声明；后台准备后的候选可以通过 `Post` 投递到 Isolate 线程。会话固定 binding 快照；刷新回调和外部根释放仍由宿主接入。`DevelopmentResult` 区分源码错误、需要 Reload、安全点等待、外部句柄等待、过期、取消和提交后刷新失败，并携带声明及冲突依赖。

## 1. 使用方式与操作边界

例如，脚本原本包含：

```vela
let score: int = 10;

func label(): string {
  return 'Score: ${score}';
}
```

运行期间 `score` 已经变为 42。将初始值改成 100，并将函数体改为：

```vela
let score: int = 100;

func label(): string {
  return 'Points: ${score}';
}
```

成功 Hot Reload 后，下一次普通调用 `label()` 得到 `Points: 42`。执行 Reload 后，新 Isolate 首次调用它得到 `Points: 100`。Hot Reload 更新未来执行的代码，不把当前状态改造成“从一开始就执行新程序”的结果。

| 操作 | 脚本状态 | 入口与初始化 | 宿主进程与 binding |
| --- | --- | --- | --- |
| Load | 在当前开发会话的程序图中加入脚本模块 | 不自动执行模块中的用户函数；全局槽按语言契约惰性初始化 | 保持运行 |
| Hot Reload | 保留对象身份、字段值、全局值、栈帧、闭包和异步任务 | 不重跑 `main()`、构造函数或已完成的初始化 | 保持运行 |
| Reload | 使用当前完整源码创建新的脚本 Isolate，丢弃旧脚本执行状态 | 重新执行入口及正常初始化 | 保持运行；向新 Isolate 注册同一套 binding |
| Restart Host | 随宿主重新启动 | 从头执行 | 重新启动宿主，属于宿主工具的操作 |

Load 和 Hot Reload 使用同一套程序图事务；Load 是增加模块的变更，不是另一套动态链接 ABI。接纳后的导出集合可供宿主解析为命名声明入口，再由宿主明确调用。新模块只能引用会话已经注册的宿主能力，不能借此修改 C++ binding。删除模块按删除其中声明的规则检查。

这里的 Reload 对应 Flutter 的 Hot Restart，也接近 React Native 的完整 Reload。React Native Fast Refresh 是框架级模块刷新，不能直接作为 Vela 语言级热重载契约。

开发工具必须让用户明确选择 Hot Reload 或 Reload。Hot Reload 被拒绝时返回原因，**不得自动执行会丢失状态的 Reload**。同一入口的失败编译不会改变正在运行的程序。

## 2. 热重载行为表

下表是本设计完成后的支持范围。“需要 Reload”表示保留状态的事务不接纳该修改；若涉及 binding 集合或 ABI，则需重新创建开发会话，不能靠脚本 Reload 改变。

| 修改 | Hot Reload 契约 |
| --- | --- |
| 修改顶层函数、实例方法、静态方法或 getter 的函数体 | 支持；提交后的普通调用进入新版本，已在执行的帧继续旧版本 |
| 修改构造函数体或现有字段默认表达式 | 支持；影响后续构造或尚未初始化的新增槽，已有实例不重新构造、不重置已有值；增删默认表达式还需满足构造调用约束 |
| 修改 `main()` 或一次性启动逻辑 | 接纳代码更新，但不自动重跑；需要重新执行启动流程时使用 Reload |
| 修改已初始化的全局变量或静态字段初始值 | 保留现值；未初始化的槽在首次读取时使用新初始化器 |
| 修改全局 `const` 初始值 | 与其他全局槽相同；Vela 的 `const` 仅禁止重新绑定，不等于 Dart 的编译期常量 |
| 新增函数、类、接口、泛型模板或模块 | 支持；完整候选程序通过类型检查，既有类型身份不变 |
| 修改泛型函数或方法体 | 支持；更新已有具体特化所对应的实现，新特化按正常编译规则生成 |
| 重排字段声明 | 支持；按声明身份对应已有槽位，不按新源码位置重排旧值 |
| 给已有类新增带默认表达式的实例字段 | 支持；存活实例的新增槽在首次访问时初始化；新实例仍按普通构造规则初始化 |
| 给已有类新增无默认表达式的必填字段 | 存在该类或其子类实例，或存留旧构造调用缺少该值时需要 Reload；不能给旧对象凭空补出合法值 |
| 删除实例字段 | 支持，但存留旧代码仍可访问该字段时拒绝；接受后清除旧值及其 GC 引用 |
| 重命名字段 | 视为删除和新增；不迁移旧值，分别满足两项规则 |
| 新增全局变量或静态字段 | 支持；新增槽为未初始化，按需执行初始化器 |
| 删除全局变量或静态字段 | 与字段删除相同；存留旧代码仍依赖该槽时拒绝 |
| 修改已有字段或全局槽的类型、可空性、可写性，或实例/静态属性 | 需要 Reload；不按当前值碰巧可转换来判断兼容 |
| 修改已有函数的参数、返回类型、泛型参数或同步/异步属性 | 需要 Reload；已有调用点、函数值和续延不能套用新 ABI |
| 删除普通函数或方法 | 候选程序必须合法；旧帧后续按声明身份调用该目标时，产生明确的目标已删除运行时错误；已有函数值仍可执行捕获版本 |
| 修改类的父类、已有类的接口实现集合、泛型参数列表或声明种类 | 需要 Reload；不在本设计内迁移继承关系或既有运行时类型假设 |
| 给接口新增或删除成员 | 完整候选实现关系有效、既有成员签名不变时支持；选择器身份不重编号；旧调用遇到已删除成员时报告目标已删除 |
| 修改枚举成员或顺序 | 需要 Reload；旧枚举值、序号及穷尽性分支不能按新定义重新解释 |
| 删除已有类、接口、枚举或改变透明别名解析后的既有类型契约 | 需要 Reload；不让仍存活的值或旧代码失去类型解释 |
| 改变旧代码中名称绑定的种类或目标，如实例调用变成静态调用 | 若仍有可执行旧版本依赖原绑定则拒绝；不根据旧机器码猜测新的词法绑定 |
| 修改 C++ binding 的实现或签名 | 不属于 Hot Reload 或 Reload；重新构建宿主并创建新会话 |
| 语法错误、类型错误、缺失导入、JIT 编译或资源准备失败 | 拒绝整个事务，继续运行原版本 |

新增字段的可空类型本身不提供默认值。`name: string?` 仍是必填字段，只有显式 `name: string? = null` 才能用于旧实例的新增字段初始化。该规则与现有构造语义一致。

修改已有函数的参数名也属于调用契约变化，因为命名实参由编译器绑定。函数重命名按删除旧声明、增加新声明处理；不提供重命名后的自动转发。修改字段访问权限时重新检查完整候选程序，并检查存留旧版本的访问依赖；不能令其继续越过新权限边界。

## 3. Dart 语义的采用范围

### 3.1 不可变函数版本与最新调用

声明身份和函数版本分开。修改函数体创建新版本，不覆写正在执行的代码。事务提交后：

1. 顶层函数调用、具体类方法调用、接口调用、静态调用和构造调用，都从最新发布的分派信息选择实现。
2. 活跃帧继续其原函数版本，从原位置执行，不重新进入函数开头；其中之后发生的普通调用仍选择最新实现。
3. 函数值捕获创建它时选定的函数版本。顶层函数值和已绑定方法值通过当前分派选定版本；绑定方法同时保留原接收者。匿名闭包的函数体与捕获布局则来自正在执行的外层函数版本：旧帧在提交后创建的 lambda 仍属于旧外层版本，不能套用新捕获布局。
4. 调用旧函数值时，它的函数体仍是旧版本，但函数体内的普通调用继续使用最新分派。新进入的外层函数创建其新版本的匿名闭包。
5. 递归调用同样是普通调用；旧帧继续运行不表示其下一次递归也必须进入旧实现。

普通调用已删除的目标时，抛出可由脚本处理的目标已删除错误，携带声明身份、调用位置和版本信息；不调用旧目标，不跳往同编号的新声明。函数值调用不属于该查找，它已持有具体版本。

最新方法选择仍遵守 Vela 既有调用语义：具体类调用使用静态解析的成员身份，接口调用按接收者当前方法表分派。`super` 使用词法所属类及父类关系描述，在当前发布信息中查找；不能把旧缓存地址当作永久目标。新增或删除覆写若会使存留旧调用的解析身份改变，按名称绑定变化规则拒绝。

“最新调用”针对已有词法绑定对应的声明身份，不重新解析正在执行的旧源码。若候选修改会使旧调用改变绑定种类或绑定到另一声明，必须先检查存留旧代码依赖；不满足时要求 Reload。这是 Vela 的明确限制，避免把 Dart 文档列出的栈上调用缺陷带入实现。

### 3.2 状态保留

Hot Reload 保留局部变量、捕获单元、对象身份、已有字段、集合内容、已经初始化的全局和静态槽，以及待完成 Future 的状态。字段按声明身份对应；字段同名但所属声明不同不表示同一字段。已有槽的初始化器改变不触发重算，`const` 引用的对象也不会被替换。

未初始化的全局和静态槽保留“未初始化”状态，首次读取选择当前初始化器。正在进行构造或初始化时暂不提交事务；待该操作完成或失败后，再在安全点重新验证。初始化失败继续遵循现有重试和 `CyclicInitialization` 契约。

Hot Reload 不回放历史语句、模块初始化、事件注册或宿主调用。用户需要重新获得从头运行的状态时使用 Reload。

### 3.3 异步、事件与框架刷新

挂在 `await` 上的续延是尚未完成的旧帧。它保留旧函数版本、局部值、异常处理信息和原恢复位置；完成后从该位置恢复，不能映射到新函数的同一指令序号。恢复后发生的普通调用使用最新实现。编辑 async 函数后新发起的调用使用新版本。

Hot Reload 不自动取消 Future、timer、微任务或宿主请求，也不重新注册监听器。队列中已经捕获的闭包按旧版本运行；若宿主希望监听器每次进入最新命名函数，应保存声明入口，而不是预先创建的函数值。两者的生命周期和语义必须在嵌入 API 中区分。

运行时提交成功后向宿主或框架发出一次“代码已更新”的通知，携带已提交的版本与变更摘要。框架可以在此后重新调用构建、布局、绘制或场景刷新入口。这一层承担类似 Flutter rebuild 的职责；语言运行时本身不重建 UI，不调用 `main()`。

刷新回调在提交之后执行。回调抛错表示“代码已提交、刷新失败”，不是热重载被拒绝；不回滚已经执行的脚本或宿主副作用。刷新动作应通过最新声明入口调用，避免通知本身永久捕获旧刷新函数。

## 4. 执行架构与模块职责

```text
源码快照 / 开发会话身份
           │
       前端检查
           │
      共享 Typed IR
           │
    共享原生语义 Lowering
       ┌───┴─────────────────┐
       │                     │
 AOT：封闭程序         JIT：可重载程序
 固定布局、直接调用     版本、分派入口、安全点
 目标文件 / 链接        LLVM ORC / 代码资源所有权
       └───┬─────────────────┘
           │
  runtime：值、GC、异常、Future、Isolate、宿主 ABI

字节码 VM：继续使用共享前端 / Typed IR / runtime 的独立执行后端
```

JIT 使用 LLVM ORC 管理目标代码的装载、符号解析、内存权限和资源回收。它不通过临时共享库或依赖系统动态链接器的文件替换实现热重载。原生代码生成从现有 AOT 后端提取公共部分，AOT 和 JIT 使用显式的编译模式，不能复制成两套语言实现。

| 层 | 责任 |
| --- | --- |
| 前端与模块加载器 | 源码快照、名称和类型检查、导入图、声明匹配、受影响依赖 |
| Typed IR | 会话稳定身份、调用和字段访问的语义、源码与失效依赖；不保存 ORC 对象 |
| 原生后端 | 共享数值、GC 保根、异常、异步、宿主 ABI lowering；按模式生成可重载分派或 AOT 直接调用 |
| JIT 编译层 | 优化和代码生成、候选代码所有权、ORC 资源与符号绑定；失败时销毁未发布资源 |
| runtime | 稳定类型身份、状态槽、分派快照、字段存储、安全点、版本保活、发布与退休 |
| 开发会话与工具 | 编译请求、版本串行化、文件监视、Load/Hot Reload/Reload、诊断、刷新通知 |
| 宿主 | 固定 binding、脚本 Isolate 所有权、外部句柄与事件解绑、框架刷新 |

runtime 不依赖编译器或 LLVM。它消费经过验证的运行时描述及拥有明确析构责任的代码资源；ORC 的具体类型留在编译层。仅链接 AOT runtime 的宿主继续无需链接 LLVM。LLVM/JIT 依赖由开发工具链提供。

首版 JIT 在发布事务之前完成所有新建或受影响函数的编译、重定位和运行时依赖解析，使用限制跨函数优化的原生基线代码；首次调用不临时触发一条未验证的装载路径。以后是否引入按需编译取决于启动测量，不改变发布契约。新源码的静态类型检查始终覆盖完整候选程序图，不以“这个函数暂时未执行”为由跳过错误。

泛型依赖同时包含新源码引用的具体特化和存留代码、对象或签名仍需使用的既有特化。即使某组类型实参已不出现在新源码的调用点，只要旧帧仍可能发起该普通调用，也必须根据新模板生成对应当前版本或拒绝不再合法的修改；不能因候选裁剪而让它误报目标已删除。模板和特化继续遵守现有静态展开限制。

字节码解释器在现有执行、调试器和 REPL 路径中继续存在。JIT 编译失败就是该 JIT 请求失败，不自动转去解释执行。是否最终删除解释器，需要另行完成全部语言路径、嵌入、REPL、调试与平台验收；本设计不以删除 `vm` 为前置条件。共享 runtime 始终需要保留。

## 5. 身份、版本与代码所有权

### 5.1 稳定声明身份

开发会话为模块、类型、函数、字段、全局槽和接口选择器分配身份。规范化模块 URI、词法所有者、声明种类与名称共同确定命名声明；泛型具体化再加入规范化类型实参。导入别名和源码行号不构成身份。移动或重命名声明视为删除和新增；不根据文本相似度推断值迁移。

这些身份不能被可达性裁剪、函数排序或紧凑化重新编号。删除后保留不可再绑定的墓碑；同名声明在后续事务中重新出现时获得新身份，不能复活旧值或让旧调用误入新声明。失败候选不消耗已发布身份。单次产物内的紧凑索引与会话身份是不同概念，必须显式映射。

Lambda 归属具体函数版本，并具有版本内唯一身份。修改外层函数允许生成全新的捕获布局；旧闭包继续持有旧布局。现有 REPL 使用行列坐标命名 lambda 的方式不作为编辑后的跨版本身份。

### 5.2 发布版本与存留版本

每次成功提交产生一个程序版本号和不可变的发布快照，其中包含类型版本、当前函数版本、选择器表、初始化器及依赖描述。运行时通过一个当前快照入口发布它，不逐项暴露半更新的分派表。一个开发会话只更新其所属 Isolate；不承诺多个 Isolate 同时提交的分布式事务。

函数版本拥有或保活机器码、恢复入口、源码快照、调试与异常元数据、常量引用、捕获布局及失效依赖。代码编译批次可以共享一个资源所有者，但回收粒度和保活关系必须可观测，不能每次修改都永久保留整个历史程序。

全局与静态值由会话状态按稳定槽身份统一拥有，旧帧、旧闭包和新代码读取同一份状态；不能随新映像复制成互相分叉的全局表。状态表扩容和字段块一样只在安全点切换，旧代码不跨安全点保留槽内存地址。字符串等代码常量则属于具体函数版本：旧函数中的字面量不因新快照的常量池排序而变成另一值。

运行时类型描述以稳定的名义身份表达参数、容器、Future 及接口约束，布局版本仅描述当前存储和方法表。新布局不能生成一个与旧值不相容的“同名新类型”；也不能让旧 `ClassLayout*` 同时承担永久类型身份与可变字段布局。固定的继承与类型参数契约使旧值、旧签名和新代码仍可进行相同的类型检查。

以下引用保活旧版本：

- 活跃脚本帧、执行中的宿主返回路径，以及优化代码中的逻辑内联帧。
- 可达闭包、已绑定方法值、显式版本函数句柄和挂起续延。
- 调试器当前暂停状态、正在展开的异常与需要读取的版本元数据。
- 尚未退出该版本安全点协议的执行片段。

结构验证需要的存留版本集合，从候选快照将继续使用的代码、上述活跃/可达引用及其版本内依赖计算，排除仅因旧发布快照尚未退休而暂时拥有的代码。集合包括旧帧未来能创建的嵌套闭包、被捕获的具体版本及构造计划；普通命名调用边则指向候选分派，并保留其原调用契约用于检查。如此既不会漏掉延迟访问，也不会让整个旧程序因一次快照引用而永远阻止字段删除。

普通命名入口持有声明身份，通过当前快照分派，不把旧机器码地址交给宿主永久保存。显式函数值持有具体版本。不能用现有 `CodeIdentity` 指针同时表示会话、程序提交和函数版本三种身份。

版本退休和代码卸载在 Isolate 所属线程协调。必须先确认所有可执行引用退出，再注销调试/展开信息并释放可执行内存；常量根与元数据按自身最后引用释放。GC 对象和 C++ 代码资源的混合所有权不能形成彼此永久保活的环。旧源码版本保留到最后一个需要它的帧或调试引用释放。

## 6. 对象布局与状态演化

### 6.1 稳定对象头与独立字段存储

封闭程序的内联字段紧接 `HeapObject`，与对象头在同一次固定大小的分配中。可重载程序中的用户类使用稳定对象头、会话类型身份和可替换的连续字段存储；字段块由堆核算并拥有精确引用扫描描述。

对象头不移动；`Value`、对象相等性、Map/Set 键、宿主已保根的对象引用以及接收者身份均保持有效。需要扩容时替换字段块，不对堆图做全量指针重写。字符串、数组、集合、Future 等内建对象的固定运行时结构不参与脚本类布局修改。

这是可重载程序的正式存储模式。封闭 AOT 程序仍可使用固定内联字段；编译产物必须明确携带存储能力和 ABI 身份，不能在首次重载时猜测对象布局或把旧 AOT 实例转换为可重载实例。首版不支持把外部预编译 AOT 用户类注入可重载类型图；两种模式仍复用值、GC、容器与宿主编解码契约。

同一开发会话内，每个具体类型的声明字段映射到不随源码重排变化的物理槽位。新增字段追加槽位；删除后不把该槽立即改作另一字段。子类的字段映射显式包含继承身份，父类新增字段不能改变子类已有字段的含义。候选布局检查及存活实例扩容覆盖受影响类型的全部子类。

同一继承字段在不同具体类型中可以位于不同槽号，不能假定父类与全部子类共享固定偏移。基线字段访问携带数字字段身份；访问点以运行时类型和布局版本缓存槽号，未命中时经数字索引解析，均摊 O(1)，不做字符串查找。快照提交后布局版本改变，旧缓存必须重新解析。已证明具体类型与布局的执行片段可以直接使用槽号，但不能把证明跨过重载安全点。

### 6.2 新增字段的初始化

Hot Reload 的准备与提交阶段不执行用户初始化器。已有实例新增的字段先处于内部“未初始化”状态，首次读取该字段时执行其当前默认表达式；若先写入，则直接保存新值并标为已初始化，不执行默认表达式。不同新增字段按实际首次读取的次序独立初始化，读取原有字段不会触发它们。正常构造的新实例继续执行现有构造顺序，所有必需字段初始化完成后才能暴露 `this`。这是新增状态在重载后的专用初始化规则，不改变普通构造语义。

默认表达式沿用现有语言边界，不能访问 `this`，不能 `await`。它可以调用脚本或宿主函数，也可能分配、抛错或产生副作用，因此只在事务提交后的正常执行中求值。每个实例独立求值；`items: int[] = []` 不让多个实例共享一个数组。

已初始化字段永不因后续默认表达式修改而重置。尚未初始化的新增槽使用读取时的最新默认表达式。读写正在初始化中的同一槽均报告 `CyclicInitialization`，不静默覆盖进行中的结果；失败恢复为未初始化，按现有初始化失败规则允许重试，不撤销已发生的外部副作用。未初始化标记不作为合法语言值逃逸给用户。

没有可用默认表达式且已有存活实例时拒绝提交；不偷偷填入 0、null 或共享对象。如果该类及子类没有存活实例，且不存在可执行旧构造或初始化版本依赖旧必填字段集合，可以接受修改，由新构造函数承担完整初始化。

### 6.3 构造调用与字段模式变化

显式构造参数列表与普通函数签名一样，在 Hot Reload 中固定。自动字段构造是例外：新增带默认值字段会增加可省略的命名实参，其可重载入口按稳定字段身份接收调用点显式提供的实参描述及值，按最新字段模式补齐缺省值；不依赖旧的参数序号代表新字段。实参仍按源码顺序各求值一次，随后按当前声明顺序执行被省略的默认表达式，再执行当前构造函数体。这里使用数字身份及静态类型描述，不在运行时按参数名字符串绑定。

存留旧调用点显式提供了已删除字段，或者省略了变更后必填的字段时，拒绝事务；不能静默丢弃实参或补入非法默认值。移除默认表达式时，还必须确认没有迁移中的未初始化槽依赖它。旧构造或默认初始化版本只要仍有机会执行，就纳入字段依赖检查。Hot Reload 不在已经开始的构造中途提交。

这一入口契约属于可重载构造的统一 ABI，不是为每次字段变化生成一层旧签名适配器。固定 AOT 构造仍可直接使用其静态参数和布局。

### 6.4 删除、字段地址与旧代码

删除字段先验证存留旧版本的字段依赖。存留集合包括旧帧、可达函数值、挂起任务和仍能被它们创建或调用的版本内代码。依赖仍存在时返回需要 Reload 的诊断；不能靠保留旧字段值使删除看似成功。删除被接纳后，清除存活实例对应槽及初始化状态，使其引用可被 GC 回收；源码重命名不额外携带值迁移信息。

生成代码按当前类型和布局验证后的字段槽号读写连续存储。任何字段块地址只可在无安全点的执行片段内借用；调用脚本、调用宿主、分配、挂起或处理重载后必须重新取得地址。LLVM 不能把可替换字段块地址提升到跨安全点的循环或寄存器缓存中。宿主也不能将字段内存地址跨这些边界保存。

字段新增初始化检查必须由生成代码和共享 runtime 一致执行；不能让旧函数按未初始化槽中的标签错误地读出数值。旧基线代码对字段块地址和初始化状态遵循同一契约，不能只改新编译的访问点。

### 6.5 GC 与事务准备

候选字段块、临时复制值、新常量及全局槽在任何可能触发 GC 前就必须保根。扩容、发布和删除操作使用统一写屏障；扫描依据当前实际存储描述，不能继续用编译时旧 `reference_fields` 扫描已变化的对象。

运行时维护按会话类型索引的存活实例登记，随分配和回收更新，不把对象额外强保活。提交前枚举受影响的类型及子类，准备其替换字段块；不通过反复全堆嵌套扫描查找每一种类型。增量 GC 的扫描进度与字段块替换在 Isolate 线程同步；释放旧字段块前必须确保没有扫描游标仍借用其地址。

实例登记或 C++ 代码资源的引用计数不等于脚本可达性。结构修改需要以“没有存活实例/旧闭包”为接纳条件时，必须在安全点完成一致的根追踪判定，可以复用 GC 的完整可达性结果；不能仅因为上一轮垃圾尚未清除就永远拒绝修改，也不能把尚未追踪的对象当作已死亡。该结构验证的扫描时间计入重载暂停。

准备失败时仅丢弃候选资源，原对象仍指向原字段块。提交阶段使用预先完成的分配和迁移记录，切换字段块、全局槽和发布快照；该阶段不执行用户代码，不存在会在切换一半时失败的内存申请。

## 7. 调用更新、安全点与优化

### 7.1 原生基线代码

可重载基线代码通过稳定声明入口或选择器读取当前分派目标；不能把可修改脚本函数的地址编成永久直接调用，包括具体类调用、递归、`super`、初始化器和 async 入口。已捕获函数值的调用可以使用其固定版本入口。C++ binding 及固定 runtime helper 使用既有受查的原生 ABI，不增加脚本版本查找。

基线允许函数内数值、控制流和循环优化，但禁止跨可重载调用边界的内联、常量传播、效果推断和目标固定。禁令覆盖 Typed IR 与 LLVM 两层，不能仅在 ORC 符号表中替换函数名。全局 `const` 是状态槽，不能把初始化值当作永恒常量；getter 的结果也不能跨可能提交的安全点缓存。

提交后旧帧返回、异常展开、闭包调用和续延恢复都仍有合法入口。原生返回地址不被修改；基线无需把活动栈映射到新源码即可保证函数版本语义。

### 7.2 安全点与提交时机

编译和机器码准备可以在隔离的工作状态中进行，只有 Isolate 所属线程可以发布。安全点至少覆盖脚本入口、调用/返回边界、循环回边、分配与运行时交互，以及 async 挂起/恢复边界；不能只依赖分配，让纯数值死循环永远无法处理请求。

到达安全点时，托管引用与逻辑帧已经按现有精确保根契约可见，且没有字段块临时地址借用。安全点检查可作为叶函数优化的真实效果，不能再仅因“不分配、不调用用户代码”而删掉必要的帧/版本信息。

执行 C++ binding 时不在宿主栈内部提交。宿主重入脚本期间的请求排队到最外层宿主借用结束后的安全点；保留所有待返回的脚本版本。脚本构造、全局或新增字段初始化未完成时延迟提交，避免把半初始化对象或初始化状态跨版本发布。长时间运行的宿主调用会增加等待时间；工具必须显示等待阶段，允许取消尚未提交的请求。

调试器暂停位置只有满足同一保根和版本条件时才能作为安全点。暂停帧继续关联旧源码；更新断点不能把旧机器指令位置套到新源码行号。

### 7.3 接近 AOT 的优化代码

单纯采用 JIT 不保证接近 AOT；间接调用、字段存储与安全点均有成本。优化层可以内联、直接调用或专化，但必须记录它依赖的函数版本、字段与类型事实、选择器及初始化假设。

优化代码发布前必须具备失效与去优化闭环：在可提交安全点记录物理机器状态到逻辑帧、局部值、GC 根和恢复位置的映射。重载影响这些假设时，先把活跃优化帧还原到**它们原函数版本的基线代码**，再发布新快照；不能跳到新函数体。旧闭包中已失效的优化入口同样回到其旧版本基线，未来普通调用仍进入最新分派。

挂起续延必须保存可恢复的版本与逻辑状态，不能只保留将被卸载的优化恢复地址。首次提供优化层时就必须支持其失效、异常路径和 async 状态转换，不能在遇到重载时临时关闭功能或继续执行失效假设。

在该闭环完成前，正式可重载模式只发布遵守上述基线限制的代码；不以“先打开 LLVM O2，以后再处理热重载”的方式引入错误语义。基线与优化代码是同一 JIT 的执行层次，不是编译失败后转解释执行的路径。

## 8. Hot Reload 事务

一次请求携带其基于的已提交程序版本，以及一组不可变源码快照。相同请求不能在编译过程中混入磁盘上后来的半次保存。未变更模块复用已确认的快照；被修改模块及其类型、泛型、调用、布局和优化依赖重新分析，直到候选程序一致。

事务按以下顺序执行：

1. **编译候选**：在前端和身份表的工作副本中解析、检查、生成 IR，建立新版本、删除集与依赖变化。此时不写当前运行时状态。
2. **准备代码**：生成并装载全部候选机器码，完成重定位、固定宿主导入核验和调试/异常信息准备。后台工作仅消费不可变编译输入与 binding 描述，不操作 Isolate 堆。未发布代码不能被普通调用看到。
3. **等待安全点**：Isolate 处理请求并验证基准版本。若期间已有其他事务提交，该候选过期；工具使用最新提交重新编译，不把旧差量强行套上去。
4. **验证运行时**：在暂停执行的同一临界区内检查存活实例、存留旧版本、初始化状态与所有结构约束。编译期间应用状态可能变化，早期预检不能代替这一步。
5. **准备状态切换**：在 Isolate 线程物化并保根候选常量与运行时元数据，枚举受影响对象，完成字段块和全局槽的资源准备，保根复制值，制定删除与退休记录；为受影响优化帧完成去优化准备。失败释放全部候选资源。提交前只生成去优化后的候选状态，不能先改变活动帧再去执行可能失败的准备工作。
6. **提交**：执行无用户代码、无可失败分配的切换，发布一个完整快照及新版本号，安装相应状态与调试映射，再恢复执行。单线程临界区内的切换对脚本与宿主观察者是一个原子点。
7. **通知与退休**：报告成功、通知宿主刷新，并按最后引用回收旧代码和字段块。

实际脚本暂停覆盖运行时验证、可达性扫描、状态准备、去优化和提交全过程，不只是最后切换快照的几条指令。布局迁移的复制工作随受影响存活实例及其字段槽总数线性增长；完整可达性判定还可能扫描其他堆图。首版不承诺硬实时最大暂停，性能报告必须包含这段总暂停，而不能把它藏在后台编译时间里。

提交前的语法、类型、结构、绑定、分配或代码生成失败均不改变已发布声明、值、分派和执行状态；错误候选也不污染后续编译缓存。取消只对尚未提交的请求有效。提交后的脚本执行错误、字段初始化错误或刷新错误遵循正常运行时规则，不倒转提交。

请求结果至少区分已接纳、源码/代码生成失败、结构修改需要 Reload、仍在等待安全点、候选过期和已取消。接纳结果携带程序版本、更新范围及分阶段耗时；拒绝结果指向具体声明和冲突依赖，例如哪个旧闭包仍会读取被删除字段。对初始化器或入口代码已更新但不会自动重跑的情况给出提示，不把成功提示写成“当前状态已被重新初始化”。

## 9. Reload：重建脚本，保留宿主

Reload 使用当前完整源码构建新的脚本 Isolate，不复用旧全局、对象、Future、timer、微任务或入口执行位置。它可以接纳 Hot Reload 禁止的字段类型、函数签名、继承或枚举变化，但仍受固定 binding 签名约束。

开发会话拥有脚本 Isolate 的切换边界与不变的 binding 注册快照。先完成候选完整编译、新 Isolate 的原生实例化和导入检查，且不执行用户入口；这些步骤失败时旧脚本继续运行。切换到达安全边界后，关闭旧脚本事件入口，停止旧调度器和任务投递，完成外部借用与句柄释放，再发布新 Isolate 并执行新入口。入口错误属于新一次运行失败，不回到已停止的旧脚本。

停止旧运行前，先由宿主确认能够释放其拥有的外部借用与根；无法完成则拒绝切换，保留旧运行。进入停止阶段后不再尝试恢复旧运行；解绑与句柄释放必须遵守已确认的生命周期协议。工具分别报告候选准备、等待宿主释放和已开始停止的状态。

Reload 不能在机器栈上仍有旧脚本帧时直接销毁 Isolate。停止请求在安全点通过专用执行状态逐层退出旧原生帧，直到最外层脚本调用返回；不能依赖跨生成代码抛 C++ 异常来跳出。此操作终止整个旧运行，不执行旧脚本的 `finally` 或继续其任务；宿主资源释放由会话生命周期协议承担。执行中的 C++ binding 先正常返回，不能被异步强行打断。所有旧执行、根和挂起状态释放完成后，才销毁其堆和元数据，并释放已无引用的代码资源。

宿主侧必须接通以下边界，才能承诺安全 Reload：

- **外部根**：现有 `RootedValue`、程序/函数句柄和外部 Future 句柄的原契约仍要求 Isolate 活得更久。不能在销毁 Isolate 后让这些句柄继续析构或读取。Reload 前由其拥有者释放；无法释放时返回需释放句柄的诊断，不强制销毁。不把旧对象引用自动搬入新堆。
- **跨线程完成**：宿主异步生产者使用可关闭、带运行代次的完成端点。关闭后投递返回已关闭，不再解引用旧堆、执行回调或访问新 Isolate。端点控制状态可以独立存活，但不保留已销毁 Isolate 的裸指针。旧消息不能仅因 ID 重用进入新运行。
- **任务停止**：不要求旧网络或文件系统操作一定能物理取消，但必须切断其脚本投递能力。不能等待无关外部操作无限期结束，也不能遗留可执行的旧微任务或恢复入口。
- **事件与资源**：宿主持有的脚本回调、订阅及定时来源在旧运行停止时解绑。脚本对宿主产生的文件、网络请求、日志或业务对象变更不会自动撤销；是否重置这些宿主资源由嵌入方的生命周期逻辑决定。
- **binding**：相同 C++ 实现与签名重新注册到新 Isolate；只刷新脚本侧包装、根和运行上下文，不重新编译或替换 binding 代码。

释放外部句柄和解绑由宿主所有权协议处理，不能靠 GC 猜测宿主是否还会使用旧值。工具的会话封装应统一管理这些资源；直接使用低层 Isolate API 的嵌入方必须显式接入相同协议。候选编译失败和宿主主动执行的解绑动作具有不同的副作用边界，不宣称宿主动作能事务回滚。

## 10. 编译增量、REPL、调试与平台

模块缓存分为持久内容缓存与会话运行状态。可复用的编译缓存必须包含源码内容、导入依赖、编译模式、目标平台、工具链及 runtime ABI 身份；代码缓存不携带另一会话的裸地址。候选基于确定源码快照，接受后才成为下一次变更的基线。文件监视器负责合并连续保存和发起请求，不能自行决定结构兼容性。

VM REPL 是追加声明和语句的事务会话，并拒绝重复声明；导入源码在 reset 前保持固定。JIT 开发控制台通过 `DevelopmentRepl` 复用交互源码构造、身份分配和候选提交机制，文件更新仍使用独立的重载事务。既有交互语句不回放；reset/退出接通代码退休、任务端点关闭和外部根释放。

调试器与诊断以“源码版本 + 函数版本 + 位置”标识帧。新源码的断点绑定新代码，仍执行旧版本的帧展示对应旧源码；去优化后保留逻辑内联栈。调试器持有的版本引用在继续、删除断点或断开时正确释放。

JIT 的每个受支持目标都必须实现可执行内存权限切换、指令缓存同步、栈展开与调试注册；ORC 集成不能假定这些工作在所有平台自动等价。macOS 的受限运行环境与移动平台的 JIT 权限是发行能力边界：未获支持的环境明确不能启动 JIT 开发模式，发布使用 AOT。不得静默降为解释执行并报告 JIT 正常。

## 12. 实施顺序与完成条件

**首先完成 H1 的契约和身份/所有权基础，再进行 JIT 接入。** 直接把现有 AOT 目标文件装进进程，无法解决状态、旧代码与 Reload 边界，不构成热重载里程碑。

| 阶段 | 实现范围 | 完成条件 |
| --- | --- | --- |
| H1：会话与生命周期 | 稳定声明身份、不可变版本、命名入口/函数值区分、候选快照、代码资源所有权；Reload 的宿主根、调度停止与完成端点契约 | 从前端到运行时的身份不被重排；旧闭包/帧/续延的所有权可追踪；失败候选不污染会话；宿主资源停止边界可验证 |
| H2：共享原生 JIT | 公共 LLVM lowering、ORC、基线调用策略、安全点、目标平台资源管理；完整同步/async/异常/宿主调用路径 | 所有现有语言生产路径在 JIT 模式通过定向与端到端验证；无未声明解释回退；AOT 仅 runtime 宿主仍可独立链接 |
| H3：状态演化与事务 | 可替换字段块、继承字段映射、lazy 新字段、全局保留、依赖拒绝、原子发布与版本退休 | 行为表中的基线支持项全部接通；包括旧构造、宿主重入、挂起任务、字段删除与 GC 压力；资源失败不产生半次更新 |
| H4：开发操作闭环 | Load/Hot Reload/Reload、源码增量、文件监视、刷新通知、REPL 与调试器集成、结构化诊断 | 嵌入测试和工具测试能重复编辑、提交、刷新、重建 Isolate；旧消息不进入新运行；外部句柄冲突能定位 |
| H5：优化与性能验收 | 依赖失效、去优化、内联/直接调用、优化续延、代码缓存与测量 | 活跃和挂起优化状态都能正确重载；旧代码可回收；性能数据同时给出冷启动、重载暂停、稳态与内存 |

H2 不能因为首个算术函数可执行就完成；H3 不能因为没有活动栈的函数体替换成功就完成；H4 不能把宿主 RootedValue 的悬空风险留给用户承担。每阶段验收覆盖生产入口、IR、代码生成、runtime、嵌入、工具和退出清理的完整链路。H1–H4 完成后才可宣称支持本文的基线热重载；接近 AOT 的性能结论需要 H5 的实测。

当前 Windows x64 实现通过 539 个 C++ 文件的静态检查、1,891 项 C++ 测试及 141 项 Python 工具与发行测试。验证包含基线和优化层的状态演化、活跃帧与挂起续延恢复、开发操作、缓存和资源退休；本轮未在 macOS 或 Linux 目标机执行验证。

## 13. 验证与性能标准

实现时至少覆盖以下可复现行为；测试断言观察返回值、状态、版本、可达性和资源计数，不用截图代替验证。

- **调用与函数值**：新调用命中新版本；旧帧继续旧语句但调用新被调函数；旧闭包/方法值保持原函数和捕获；删除目标给出受查错误；递归、接口及 `super` 遵循对应规则。
- **初始化与对象**：保持相等性、宿主根及集合键；字段新增、重排、删除、重命名和父类字段扩展正确；默认数组不共享；首次写入跳过默认表达式；未初始化槽、初始化失败重试和 `const` 保留值符合契约。
- **类型与拒绝**：逐项覆盖行为表中需要 Reload 的修改、旧访问权限/绑定冲突及存留旧代码的字段依赖，拒绝后原版本继续执行。
- **事务与故障**：在候选编译、重定位、常量和字段块准备中注入失败；并发保存导致候选过期；取消和初始化忙碌时没有部分提交。提交后刷新失败与提交失败有不同结果。
- **GC 与寿命**：GC stress 下更新字段块、全局、闭包与续延；可达旧版本不卸载；释放最后引用后代码、元数据和常量可回收；反复重载不随历史次数无界积累整代程序。
- **异步与宿主**：覆盖 await 前后、错误完成、取消、timer、队列旧回调和宿主重入；Reload 时外部根未释放、跨线程迟到完成与不可物理取消的请求均不访问已销毁 Isolate。
- **调试与平台**：旧新源码并存、断点和异常栈、优化去优化、线程归属、可执行权限及指令缓存；各支持平台的构建、发行和 AOT runtime 独立宿主链接。

性能使用相同目标和 Release 构建、可比的语言语义，对比 C++、封闭 AOT、可重载 JIT 基线和优化 JIT，并注明各自优化策略。分别记录：

| 指标 | 测量边界 |
| --- | --- |
| 冷启动 | 源码装载、检查、IR、JIT 编译、链接/重定位、实例化与首次执行分别计时 |
| 热重载延迟 | 增量编译、代码准备、安全点等待、运行时验证、对象准备、提交和框架刷新分别计时，另报暂停到恢复的总时间 |
| 稳态吞吐 | 排除编译与预热，保留分派、安全点、字段存储和正常 GC 成本 |
| Reload | 完整编译、新 Isolate 准备、旧运行停止与入口重跑分别计时 |
| 内存 | 堆、字段外部块、常量、编译峰值、可执行代码、调试元数据与被保活旧版本分别统计 |

现有统一报告的 24 项负载（8 项原生负载及 16 项 dasProfile 移植负载）继续作为完整对照集合，在同机 Release 构建上覆盖 C++、VM、封闭 AOT、可重载基线和优化 JIT；这 16 项属于 24 项集合，不重复计数。另测频繁编辑、存活旧闭包、大量旧实例及大量挂起任务。算术或字段用例若被 C++ 整体化简，应单列，不用其极端倍率推导 JIT 收益。宿主、分配和字符串库成本单独解释。

`python -m tools.vl bench --jit-compare` 对比同一套 C++、VM、封闭 AOT、可重载基线和优化层，并运行 `hot/` 重载负载。报告将完整运行时暂停与后台编译分开，提供各阶段耗时、首次执行、字段块、代码、常量/调试载荷和旧版本释放前后的计数。进程 resident 高水位在编译结束时采样；要将它归因于某个编译负载，应在独立进程只选择该用例。操作系统文件缓存和已启动进程的状态不等同于冷机器启动。运行方式和计数边界见 [benchmark 说明](../../benchmarks/README.md)，汇总按仓库规则保留在 [`rolling_summary.json`](../../benchmarks/results/rolling_summary.json)。

“接近 AOT”在完成这些测量后按用例和几何平均报告 JIT/AOT 比值，不预先承诺固定倍数。报告必须包含基线与优化层的差异，不能以关闭热重载约束的代码冒充可重载 JIT。若墓碑或用户保留的旧函数值造成会话增长，工具给出资源统计和显式 Reload 入口，不自动丢弃用户状态。

2026-10-30 的 Windows x64 Release 测量使用 Ryzen 9 7900X，覆盖五后端的 24 项共同负载及 18 个重载入口。138 个入口的七次随机交错采样共 966 个样本，均通过完整性、校验值和资源释放检查。基线及优化 JIT/AOT 的几何平均分别为 **13.06×、13.57×**；排除单列的算术与字段用例后，其余 22 项分别为 **9.11×、9.34×**。本轮未显示优化层的整体收益，尚不能宣称接近 AOT。不少用例的变异系数超过 10%，不把两档 JIT 的小幅整体差异视为已确认的稳定回归幅度。

另以 28 个独立进程覆盖两套完整源码和两档 JIT，记录装载、首次工作负载执行及编译进程 resident 峰值；dasProfile 输入准备位于装载之后、首次工作负载计时之前，其耗时不包含在装载或首次工作负载耗时中。重载测量中的最大观察暂停为 **2.491 ms**，包含运行时验证、GC、迁移、去优化及发布，不代表暂停上界。保留旧闭包或续延的用例在最后引用释放后均只剩一个当前代码批次。各用例的中位数、变异、阶段耗时、内存及源码和工具链身份以 [`rolling_summary.json`](../../benchmarks/results/rolling_summary.json) 为准；其前一次记录的机器与测量范围不同，不能直接比较回归幅度。
