# JSON 强类型解码设计

[English](../en/typed_json.md) | [**简体中文**](typed_json.md)

> 状态：M0–M5 已完成，macOS arm64 上的编译、回归、静态检查、独立 AOT 与 Release 测量通过。原生分发的两项环境跳过及未验证平台见第 11 节。

目标类型 `T` 直接定义 JSON 输入契约。解码器检查完整输入，构造真正的 `T`，调用方无需另写 schema 或使用 `as`。

```vela
class User {
  name: string;
  age: int;
  nickname: string? = null;
}

func main(): void {
  const result = JSON.safeParse<User>('{"name":"Vela","age":18}');
  if (result.success) {
    const user = result.value; // 静态类型为 User，运行时也是 User 实例。
    print(user.name);
  } else {
    const error = result.error;
    print('${error.path}: ${error.message}');
  }
}
```

## 1. API 与类型选择

标准类统一命名为 `JSON`，覆盖动态 parse、泛型 parse、safeParse 和 stringify；不保留 `Json` 别名、双重注册或旧名回退。新结果和错误类型分别命名为 `JSONParseResult<T>`、`JSONParseError`。

| 调用 | 结果与失败行为 |
| --- | --- |
| `JSON.parse(source: string): dynamic` | 重命名后的动态 JSON 解析；无效输入抛出 `Error(code: 'JsonDecodeError')` |
| `JSON.parse<T>(source: string): T` | 强类型解码；输入无效时抛出 `JSONParseError` |
| `JSON.safeParse<T>(source: string): JSONParseResult<T>` | 强类型解码；输入无效时返回失败结果 |
| `JSON.stringify(value: dynamic): string` | 继续遵循现有 JSON 编码契约 |

这些标准静态方法无需 import。泛型调用中的 `T` 必须显式给出；泛型函数可转发自己的类型参数，具体应用时完成可解码性检查。`JSON.safeParse(source)` 缺少目标类型时报告编译错误，不默认选择 `dynamic`。无类型参数的 `JSON.parse(source)` 始终返回 `dynamic`，预期赋值类型不得悄悄改变解析语义。

`JSON.parse` 的函数值仍为 `(string) => dynamic`；显式特化的 `JSON.parse<User>`、`JSON.safeParse<User>` 分别为 `(string) => User`、`(string) => JSONParseResult<User>`。标准声明、特化和工具必须共同表达这两种 parse 调用形态，不通过给普通用户函数增加重载或默认泛型实参来实现。

`source` 只接受字符串。该 API 不接收任意现有 `dynamic` 对象，也不提供 stringify 后重新 parse 的转换路径。已有动态对象的 nominal 类型检查继续使用 `is`；静态已知的内部接口直接声明准确类型。

## 2. 成功与失败结果

`JSONParseResult<T>` 是由标准库创建的名义结果类型，无公开构造函数，判别状态不可修改。公共只读属性为：

| 属性 | 静态类型 | 有效状态 |
| --- | --- | --- |
| `success` | `bool` | 两种状态 |
| `value` | `T` | 成功 |
| `error` | `JSONParseError` | 失败 |

逻辑结果形状如下；这是状态说明，不是新增的对象字面量语法：

```text
成功：{ success: true, value: User(name: 'Vela', age: 18) }
失败：{ success: false, error: JSONParseError(...) }
```

成功结果仅保存成功载荷，失败结果仅保存错误载荷。读取不属于当前状态的属性通过普通异常路径报告 `Error(code: 'TypeError')`，不返回伪造的 `T`、默认值或 `null`。调用方按 `success` 分支后可直接读取 `value: T`，不依赖可空字段收窄，也不要求新增通用联合类型或字段判别收窄语法。经由 dynamic、闭包或普通方法读取结果时，遵循相同检查。

`JSON.safeParse<User?>('null')` 成功，`success == true` 且 `value == null`。这与 `JSON.safeParse<User>('null')` 的失败结果不同。结果状态不可变不代表成功对象不可变；`User` 及其容器仍遵循普通可变性规则。

`JSONParseError` 由解码器创建，无公开构造函数；得到的错误对象可直接抛出，并由 `catch (error: JSONParseError)` 捕获。该标准名义类型具有以下只读属性：

| 属性 | 类型 | 含义 |
| --- | --- | --- |
| `code` | `string` | 稳定的输入错误分类 |
| `path` | `string` | 从 `$` 开始的输入路径 |
| `expected` | `string?` | 目标类型；无对应类型时为 null |
| `actual` | `string?` | 实际 JSON 类型；缺失字段使用 `missing` |
| `offset` | `int?` | 已知时为从零开始的原始 UTF-8 字节偏移，否则为 null |
| `message` | `string` | 面向读者的原因说明，文案不作为稳定标识 |

`JSON.parse<T>` 抛出的错误与同一输入的 safeParse 失败载荷具有相同字段。它们使用一个解码实现与一种输入错误模型。

## 3. 可解码类型

| 目标类型 | 接受的 JSON 值 |
| --- | --- |
| `bool`、`string` | 相同种类的标量 |
| `int` | 不含小数点和指数、且在有符号 int64 范围内的整数 token |
| `double` | 含小数点或指数、可转换为有限 binary64 的数值 token |
| `T?` | null 或可解码为 T 的值 |
| `T[]` | 数组；逐元素解码并创建真正的 T[] |
| `Map<string, T>` | 对象；按键插入顺序逐值解码并创建该具体 Map |
| 可解码的具体 class | 对象；按第 4 节的构造参数契约解码 |
| `dynamic` | 现有 JSON 值模型：基础值、dynamic[] 和 Map<string, dynamic> |
| 透明类型别名 | 展开后按实际目标类型处理 |

这些规则递归应用于泛型实例与嵌套容器。数字种类沿用[现有 JSON 语义](json.md)：`1` 不自动变成 double，`1.0` 不自动变成 int；字符串、布尔值不参与数值转换。有限浮点值保留现有舍入、次正规数和带符号零行为。

`void`、函数、接口、枚举、Set、Future、字节存储、正则及其它具有专用运行时构造语义的标准对象不可自动解码。Map 的键必须为 string；不把字符串键自动解析为其它类型。不根据相同成员名满足接口，不根据额外标签推断子类。上述不可解码类型即使嵌套在可空类型或空容器中，也在编译期拒绝。普通用户 class 的可解码性由其构造契约决定，不能仅凭运行时对象布局判断。

规则性的递归类型允许通过计划节点的引用形成闭环，例如 `Node` 中的 `Node?` 或 `Node[]`。不断增长的泛型实例仍遵循[既有特化限制](generics.md)，报告编译诊断，不生成无限计划。JSON 数据本身是有限树，不恢复对象身份、循环引用或共享引用。

## 4. 类与构造参数契约

解码器必须调用目标类的公开构造路径，不直接写对象内存，不绕过 private，不把 Map 的布局当作 class 布局。输入键精确匹配构造参数名，区分大小写。

| 构造形式 | JSON 对象契约 |
| --- | --- |
| 生成的字段构造，包括 `constructor { ... }` | 使用当前类公开实例字段产生的具名参数；无初始化器者必填，有初始化器者允许省略 |
| 显式 `constructor(name: Type, ...)` | 使用完整显式参数列表；不额外接受字段名，所有当前语言中的显式参数均必填 |
| 显式 `constructor()` | 只接受空对象，然后执行普通默认初始化和构造体 |
| 非公开构造函数 | 目标类型在编译期不可解码 |

继承类只使用自身构造签名；基类参数与 `super(...)` 按[现有构造规则](core_language.md#按字段生成的类构造模型)执行。private、static、getter、setter 和普通方法不增加 JSON 键。显式参数可以在构造体内设置 private 字段，这是普通构造行为。

缺失与 null 必须区分：`nickname: string?` 仍然必填；`nickname: string? = null` 才允许省略。显式 null 不触发默认值，非可空目标会失败。存在但类型错误的值不能退回默认值。默认表达式只在缺失时执行一次，遵守当前字段声明顺序；每个实例的可变默认对象独立构造。

显式输入值按数组索引、Map 插入顺序或 class 构造参数声明顺序物化。子值先于父构造完成；随后按普通构造规则执行被省略的默认值及构造体。JSON 键的书写顺序不改变 class 构造参数的物化顺序。

未知键一律报告 `unknown_field`。即使键与某个非构造参数字段同名，也不能赋值或静默忽略。第一版没有忽略未知键、改名、默认值覆盖、枚举映射、自动日期转换、schema 对象或用户解码钩子。自定义构造函数已有的验证、计算和异常行为保持普通调用语义。

## 5. 校验顺序与错误边界

一次调用分为完整语法解析、完整目标结构校验、强类型物化三个阶段。语法或结构失败时，不运行任何用户字段默认表达式或构造体。结构校验全部通过后，才按构造和容器规则物化结果。

| `code` | 触发条件 |
| --- | --- |
| `syntax_error` | JSON 语法、转义、UTF-8、尾随数据等不符合现有严格语法 |
| `number_out_of_range` | 输入数值超出既有 JSON int64 或有限 binary64 范围 |
| `type_mismatch` | JSON 种类与目标不符，包括非可空位置的 null |
| `missing_field` | 缺少必填构造参数 |
| `unknown_field` | 对象包含构造签名之外的键 |

只返回首个输入错误。先完整解析语法并检查数值可表示性；通过后按目标结构深度优先校验。数组使用索引顺序，Map 使用输入插入顺序；class 对象先检查必填参数是否存在，再检查未知键，最后按构造参数声明顺序递归检查值。多个缺失参数取声明顺序中的第一个，多个未知键取输入顺序中的第一个。

沿用现有重复键规则：最后一个值生效，保留首次插入位置；强类型结构校验使用该逻辑对象。完整解析的数值范围检查覆盖所有 token，包括重复键中被后值覆盖的数值。字段名先按 JSON 转义解码，再匹配构造参数。私有字段名的输入只能得到普通 unknown_field，不泄露其类型。

路径根为 `$`，数组为 `[2]`。符合 `[A-Za-z_][A-Za-z_0-9]*` 的对象键使用 `.name`，其它键使用 JSON 字符串转义的 `["key"]` 形式，例如 `$["display.name"]`。缺失字段的 offset 为 null；有对应 token 的错误保留其起始字节偏移；语法错误沿用解析器的错误偏移和已确定的最近结构路径，无法确定时使用 `$`。`actual` 使用 `null`、`bool`、`int`、`double`、`string`、`array`、`object` 或 `missing`，不把完整输入复制到错误中。

`unknown_field` 的 offset 指向未知键 token，`actual` 描述该逻辑键最终生效的值种类，`expected` 为 null。

`safeParse` 只把上述输入错误变成失败结果。source 求值错误、内存不足、取消、执行预算或调用深度限制，以及默认表达式、构造体抛出的异常继续沿普通执行路径传播。不能使用 catch-all 将这些失败包装成 JSON 不匹配。物化阶段的用户副作用不保证回滚；其异常不发布成功结果，但用户代码自己暴露的对象仍由普通所有权契约约束。

即使用户构造体主动抛出一个 JSONParseError，也不能被当作本次解码的输入失败吞掉。解码阶段的失败结果与用户异常使用明确的来源和状态区分，不能仅按异常类型捕获。

## 6. 编译与运行时链路

| 责任方 | 必须交付的契约 |
| --- | --- |
| 标准声明与前端 | 将标准类及保留名称迁移为 JSON，删除 Json 注册；公布 API、结果属性和错误类型；完成具体 T 的可解码性、可见性、参数绑定与递归闭包检查 |
| SemanticModel | 按规范类型身份提供唯一的解码计划图：构造调用目标、参数名与类型、必填/默认标记、容器和递归边；后续阶段不重新猜测 schema |
| 泛型与 IR | 用现有特化事实生成具体解码入口与普通构造调用；结果 value 保持 T；两种强类型 API 共用计划 |
| runtime/json | 复用现有严格 JSON 解析和数值规则，提供有偏移的文档访问、迭代校验状态和结构化输入错误 |
| native、JIT 与 AOT | 共享物化过程、结果访问器和异常边界；用户构造运行于普通受检查调用帧，保留 GC 和源码栈契约 |
| 缓存、镜像与发布 | 纳入解码计划、目标类型、构造签名、默认省略契约和生成入口；独立产物无需编译器或源码反射 |
| LSP、doc、fmt 与 REPL | 使用同一标准声明与特化事实，显示准确泛型签名、结果属性、构造引用和不可解码位置的诊断 |

实现将现有解析器产生的原始 JSON 文档保留到物化完成，不先构造完整 dynamic 托管图再逐节点复制。校验与物化消费同一个规范解码计划。现有动态 parse 可继续通过其原生值物化路径消费同一个语法解析生产者；不得保留两套有不同错误或数字规则的 JSON 解析器。

泛型定义中的 JSON 泛型调用登记可解码性特化义务，并沿普通泛型调用关系传递；具体应用必须完整检查其闭包。该义务不授予普通类型参数反射、任意成员访问或 `T()` 构造能力，也不能通过 dynamic 擦除逃避检查。

运行时存在性标记必须独立于参数值，保证“省略”与“显式 null”不同。复用普通构造绑定和默认初始化的权威实现，支持运行时决定某个默认参数是否省略；不能为 n 个默认字段枚举 2^n 个调用分支，也不能在解码器中复制一套默认表达式执行规则。实例字段最终初始化和构造体执行仍走普通类构造契约。

使用迭代遍历状态处理深层数据，不把不可信 JSON 深度直接映射成 C++ 递归栈。对象成员查找为每个对象建立一次索引或等价线性处理，不能对每个参数重复线性扫描全部键。设输入长度和可达输出总规模为 n，解析、校验与物化总体为 O(n)；类型计划构建单独按可达具体类型和成员规模计量。

## 7. 所有权、缓存与性能

原始文档、字段索引和遍历暂存区由一次解码会话拥有并参与现有 heap 外部内存统计。source 借用、文档访问与原生帧之间的存活期明确绑定；调用用户代码前，所有暂存托管值和部分构造图必须保根。正常返回、输入失败、用户异常和资源失败都释放会话暂存资源。

结果、错误字符串和强类型图归当前 Isolate 所有，不借用 source、解析 arena 或编译器对象。失败结果不保留整个输入文档、完整输入字符串或部分构造图；不可回收的用户主动暴露对象不属于自动回滚范围。错误对象或结果对象分配失败走 OutOfMemory，不伪造失败载荷。

缓存身份覆盖规范 T、构造输入契约、递归计划和标准库实现。类型/构造契约改变必须触发现有对应失效或 Reload；实现体更新遵循现有版本协议，活动帧持有与之配套的旧计划和调用目标。AOT 可达性必须保留被计划引用的构造、默认初始化、结果与错误布局，并清理不可达特化。

完成验收时使用 Release 测量标量、对象、大数组、嵌套泛型、早期/末尾结构失败和构造体开销。分别报告耗时、首次调用分配、峰值内存及完整 GC 后保留量；与相同验证契约的手写解码器比较。已测结果和比较边界见第 10 节。

## 8. 内部工具迁移与命名

只对确实接收 JSON 文本、随后逐字段转换的生产路径迁移为强类型 JSON API。sdk:test / sdk:mock 的原生桥返回值、函数返回值和已存在的对象，不允许先编码 JSON 再解码。其操作码与 dynamic 返回值问题应通过准确的桥接口、记录类型和普通 `is` 收窄解决；不能用新的解析 API 掩盖签名问题。

新公共 API、生成解码入口和相关自有辅助声明不以下划线开头；内部可见性通过非 export 或 private 表达。用户 JSON 键保持原样，不因命名规范更名。SDK、mock 生成器、对应原生绑定和 Python 工具的既有自定义下划线前缀名称列入独立迁移面，删除旧名称而不保留别名；语言/平台规定的协议名称不进行风格改写。`import ... as ...` 的模块别名语法不属于类型转换。

## 9. 实施阶段与完成条件

各阶段按下表验收。阶段通过不代表整个功能完成；必须接通全部生产路径、删除被替代的重复逻辑，并完成本节验收后再标记交付。

| 阶段 | 实施面 | 完成条件 |
| --- | --- | --- |
| M0：声明与结果 | Json → JSON 全量改名、标准 API、名义结果/错误、只读访问、显式 T 与函数值 | 成功 value 为 T；失败无伪载荷；合法 null 可与失败区分；错误状态访问受检查 |
| M1：可解码性与计划 | 泛型、别名、构造签名、默认省略、递归闭包 | 不可解码成员精确定位；计划身份唯一；不新增反射或开放泛型宿主 ABI |
| M2：校验与物化 | 文档访问、标量/容器/class、字段存在性、普通构造 | 输入错误不执行用户代码；默认与显式参数契约完整；错误路径和顺序稳定 |
| M3：执行与生命周期 | JIT/AOT、GC、异常、受限执行、独立发布 | 两后端等价；所有退出路径释放会话；脱离编译器执行；活动旧版本保活 |
| M4：工具与迁移 | LSP/doc/fmt/REPL、缓存、真实 JSON 消费者及全部自有示例/测试/文档中的标准类引用 | 无零散 as 的 JSON 解码生产路径；无旧重复解析器、残留入口或下划线生成名 |
| M5：统一验收 | 全量回归、静态检查、发布检查、Release 测量 | 下表全部满足；环境跳过与未验证平台明确记录；更新本文状态与路线图 |

内部 SDK 桥接口及下划线命名迁移单独记录其完成范围，不以 JSON.safeParse 的交付替代这些工作的验收。

SDK 迁移范围包括 `sdk:test`、`sdk:mock`、mock 生成器、原生绑定及 Python 工具中的自定义下划线前缀声明。原生操作码封装为具名、准确签名的桥接口；trace 使用五参数 callback，组合 matcher 使用 `Matcher[]`。保留的四处 checked cast 集中在真实的动态边界：测试工具对任意泛型容器的长度与键查询，以及 mock 在响应签名验证后恢复返回载荷 `R`。它们不接收 JSON 文本，也不通过 JSON 往返转换已有对象。

## 10. Release 测量

2026-11-02 在 Apple M1 Pro、macOS arm64 上使用 Release、Clang 23 和 LLVM 21.1.8 测量。每个用例在独立进程中运行 7 次，Google Benchmark 的最短测量时间为 0.3 秒；编译和输入准备不计入耗时。本节保留该次测量的聚合结果；[滚动基准摘要](../../benchmarks/results/rolling_summary.json)随后续基准运行更新，仅保留最近两次完整运行。基准实现见 [typed_json_benchmark.cc](../../benchmarks/typed_json_benchmark.cc)。

| 用例 | 强类型中位耗时（µs） | 手写中位耗时（µs） | 强类型 / 手写 |
| --- | ---: | ---: | ---: |
| 标量 | 0.429 | 0.254 | 1.687 |
| 对象 | 0.706 | 0.796 | 0.887 |
| 1024 元素数组 | 375.666 | 652.250 | 0.576 |
| 嵌套泛型 | 344.550 | 635.383 | 0.542 |
| 首元素结构失败 | 118.214 | 4167.124 | 0.028 |
| 末元素结构失败 | 222.033 | 5751.728 | 0.039 |
| 含构造体的数组 | 442.669 | 704.627 | 0.628 |

下表每格依次为强类型 / 手写。分配量是首次调用累计成功分配字节数和次数，包含托管块与 Heap 核算的外部块；峰值是相对编译后基线的 Heap 活跃字节增量。14 个用例的完整 GC 后保留量均为 0 字节。

| 嵌套泛型 | 1639665 / 1527425 | 3088 / 8247 | 1491945 / 1289664 |

手写基线针对这些固定的 int、Item 和 Box 输入，先用动态 parse 检查完整语法，再完整校验结构后调用构造体；失败时另行恢复原始 UTF-8 偏移，并检查 code、path、expected、actual 和 offset。比较不覆盖任意目标类型、语法或资源失败、名义结果 API。失败用例的比例包含手写偏移恢复成本，不能解释为纯语法解析速度差。

本次墙钟耗时变异系数最高约 29%，表中仅报告本次中位数；标量存在固定会话开销，大数组成功路径的累计分配字节及 Heap 峰值也高于手写基线。摘要另存的进程 RSS 峰值包含 JIT 编译，不代表解码器独占峰值。上述结果不构成普遍加速、零分配或跨平台性能保证。

## 11. 验收范围

macOS arm64 上的 Debug 默认产物和全部测试目标、Release 基准目标均构建通过。base、frontend、IR、runtime、AOT、JIT 和 compiler 七个 C++ 套件共 2330 项测试通过；其中最终 compiler 全量回归为 1213 项。JSON 的专门验收还覆盖小 heap、逐分配点失败、深层递归、停止请求、构造栈限制、缓存失效、热重载及活动旧版本保活。独立 AOT 工具验收两项通过，其 native host 包含 58 项检查。

Python 工具回归 162 项中 160 项通过，另两项原生分发测试因当前环境未提供已审计的 `VELA_TEST_TARGET_SUPPORT_SPEC` 而跳过：打包后的语言语料 JIT/AOT 对照，以及打包构建与无源码运行。独立链接 native host 的验收不依赖这项配置，已经通过；Windows、Linux 和其它架构仍未验证。

全仓 `vl lint` 检查 666 个 C++ 文件及头文件，零失败；`bugprone-unchecked-optional-access` 保持启用。变更 C++ 文件的格式以及所有变更文件的 UTF-8、LF、结尾换行、文档相对链接和 `git diff --check` 均通过。SDK 桥签名及自有下划线命名迁移的完成范围遵循第 8、9 节，保留的四处 checked cast 均位于已说明的动态边界。
