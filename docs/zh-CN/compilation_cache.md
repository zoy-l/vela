# 字节码镜像与编译缓存

[English](../en/compilation_cache.md) | [**简体中文**](compilation_cache.md)

`vela compile source.vela output.vbc` 将字节码镜像写入磁盘文件而不立即执行。`vela exec output.vbc` 加载并严密校验该镜像，随后以与 `run` 命令相同的退出码和错误诊断规则执行 `main` 函数。执行字节码镜像无需依赖原始源文件存在；源文件路径和 PC 映射信息依然完备，可用于生成精准的调用栈。

`vela run source.vela` 默认在其当前工作目录下使用 `.cache/vela` 缓存目录。宿主嵌入 API `CompileFileCached(path, cache_directory, isolate)` 返回 `Hit`（命中）、`Absent`（缺失）、`Stale`（过期）和 `Invalid`（无效）状态。`CompileFile` 仍作为显式的非缓存编译接口保留。系统不使用全局缓存目录或环境变量来定位缓存。

## 缓存身份与失效机制

缓存键采用规范化后的请求入口文件绝对路径。缓存元数据包含：

- **SHA-256 构建指纹**：由 `vl config` 计算，覆盖编译器、运行时、VM、基础库、构建配置、目标系统/CPU 及固定依赖声明。
- **XXH3-128 内容指纹**：覆盖模块加载器实际消费的每一个源文件，包括被引用的默认标准库声明。
- **规范化路径信息**：记录每一个被请求源文件路径及其规范化物理路径，因此即使旧目标内容未变，改变软链接指向也会使缓存立即失效。

文件修改时间（mtime）和文件大小绝不足以判定缓存命中。判定命中前必须读取所有依赖文件并计算指纹，校验规范化路径，随后加载并验证镜像；命中时将完整跳过词法分析、语法分析、类型检查、泛型特化、IR 生成及字节码编码。未保存的编辑器内存缓冲区直接使用常规模块检查器，不走磁盘缓存。

缓存容器具有独立的校验和，覆盖元数据与字节码内容。其 `VELACCH2` 模式仅存储源文件指纹与路径解析结果。过期或损坏的缓存项将自动从源码重新构建。编译失败不会覆盖先前有效的缓存项。缺少原生符号或签名发生变化将阻止加载镜像；重新构建过程会执行常规的原生绑定诊断。I/O 错误作为明确的 API 错误返回；CLI 工具以 sysexits `74` 退出。

写入缓存时，先在目标目录下写入带唯一临时命名的文件，随后通过 `std::filesystem::rename`（在 Windows 标准库下为 `MoveFileExW`，在 POSIX 下为 `rename`）执行原子替换。写入失败绝不会破坏原有的缓存项。竞争写入时完整发布整份镜像。这保证了可见性的原子性，但并不承诺所有目录元数据在断电时立即可恢复。

## 镜像格式与所有权模型

版本 2 镜像以 `VELABC01` 幻数开头，包含小端序 uint32 版本号及 XXH3-128 有效载荷校验和。数量计数、文本长度和图节点标识均使用 uint64。镜像中绝不序列化任何原始指针、原生 C++ 对象布局、堆内存快照或运行时全局状态。整数保留完整 64 位；浮点数保留其二进制位模式。

镜像有效载荷包含：类/数组/集合图定义、共享布局表、保根字符串常量池、源码路径表、函数定义、异常处理器、源码映射表、原生函数名与确切签名，以及全局初始化器 ID。数组与集合图的重构采用拓扑遍历迭代算法；能够准确诊断循环引用与缺失引用。在实际内存分配前，所有数量计数都受到剩余输入字节数的严格边界约束。`Program::Create` 在完成反序列化重构后、正式执行前，会全面校验指令代码及跨函数跳转目标。

镜像加载过程会将目标 Isolate 中的原生符号进行链接绑定，并创建全新的内存布局、根集合及惰性全局状态。加载完成后，原始镜像字节及源 Isolate 可以安全销毁。目标 Isolate 的生命周期必须长于加载后的程序及其句柄，这与全新编译出的程序要求完全一致。

字节码镜像是带有损坏检测的受信任编译器制品。校验和用于防范数据损坏，并不对生产者进行密码学鉴权；字节码验证器亦非安全沙箱，不能取代宿主环境的安全信任策略。不支持任何不同版本的镜像；不保留任何旧版本兼容镜像加载器。

## 验证与平台契约

GoogleTest 全面覆盖了独立 Isolate 所有权、GC 压力测试、闭包、接口、泛型、集合、异常、整型/浮点/字符串常量池、各种截断损坏、校验和失真、结构畸变的载荷、原生签名变化、源码变动失效及 Unicode 路径。文件系统测试覆盖了空文件、替换失败、并发读写及保留旧快照的并发读取。Windows 平台的发布采用带有 replace/POSIX 语义的 `SetFileInformationByHandle(FileRenameInfoEx)`；并发替换不会陷入 `MoveFileExW` 常见的删除挂起竞争。其它平台采用同目录原子重命名。不使用任何轮询重试循环或“先删后写”的非原子路径。Vela 的 Windows 读取端以 `FILE_SHARE_DELETE` 共享模式打开文件，在替换产生新可见镜像的同时，允许现有读取方继续完整读取旧快照。其它未开启删除共享打开句柄的外部软件仍可能阻止替换操作。Win32 重命名缓冲区包含了结尾的 UTF-16 终止符（尽管 `FileNameLength` 不计入它）；单元测试覆盖了各种文件名对齐边界与并发快照读取。参考微软官方 [重命名标志说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)。
