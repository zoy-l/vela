# 泛型约束与推导

[English](../en/generics.md) | [**简体中文**](generics.md)

Vela 支持泛型声明、单一上界和约束驱动推导。本文规定其声明、静态检查、具体执行和工具契约。语法采用 Dart 风格，保留 Vela 的基本类型、显式数值转换、容器不变性、受检查 dynamic、单态化和紧凑存储。

```vela
interface Comparable<T> {
  compareTo(other: T): int;
}

class Score implements Comparable<Score> {
  value: int;

  compareTo(other: Score): int {
    return this.value - other.value;
  }
}

func compare<T extends Comparable<T>>(left: T, right: T): int {
  return left.compareTo(right);
}

func main(): int {
  return compare(Score(value: 42), Score(value: 40));
}
```

`T extends Comparable<T>` 表示具体类型必须显式实现适用于自身的比较接口。类型参数仍具有独立身份，不被替换成上界类型；推导和约束检查结束后，后端消费具体特化及已解析的调用目标。

## 1. 目标与兼容边界

本设计完整覆盖泛型声明、定义检查、类型应用、实参推导、函数值具体化、接口分派、跨模块使用、工具和持久化。完整指这些生产路径使用同一语义契约，不指实现 Dart 的全部类型和全部泛型表示方式。

| 采用的能力 | Vela 的规则 |
| --- | --- |
| 单一上界 | 每个类型参数至多一个 `extends` 上界，按静态类型关系验证 |
| 参数化上界 | 上界可以包含其它类型参数、已有类型构造和限定类型名 |
| 参数间依赖 | 支持 `U extends T`，不依赖参数的书写顺序解析名字 |
| 自引用约束 | 支持 `T extends Comparable<T>` 等具有类型构造的递归约束 |
| 泛型定义检查 | 在未实例化时按类型参数和约束检查，不能依靠某次具体实参补出未声明能力 |
| 约束驱动推导 | 统一处理实参、预期类型、回调、名义父类型投影和声明上界 |
| 单态化交付 | 显式与推断使用相同的规范化特化身份，执行签名中没有未求解类型参数 |

以下边界是语言选择，不能在实现中作为兼容路径偷偷放宽：

- 不新增 Dart 的 `Object` / `Object?` / `num` / `Never` 类型层级，不建立 int/double 的隐式转换或共同数值上界。
- 用户泛型实例及可变数组、Set、Map 保持类型参数不变性。Future 等已有 API 的载荷适配遵守各自现有契约，不形成全局泛型协变。
- 函数赋值、参数数量、方法重写和受检查 dynamic 保持现有契约；本设计不引入一般函数子类型或 Dart 的 `covariant` 参数修饰。
- 不提供交叉上界 `A & B`、联合类型、结构化成员约束、`keyof`、条件类型、映射类型或关联类型。
- 不提供类型参数默认值或 Dart 的 instantiate-to-bound 默认实参规则。上界参与求解，但不能仅因缺少证据就把上界填成类型实参；无法确定结果时要求显式实参。
- 泛型函数和方法可以按普通函数上下文具体化；不新增可在运行时反复应用不同类型实参的多态函数值、泛型 lambda 或运行时泛型代码生成。
- external 及宿主原生符号继续暴露具体签名，不增加开放泛型宿主 ABI。

上下文规则见[类型推导](type_inference.md)，值和容器规则见[核心语言](core_language.md)，完整可运行示例见 [`examples/generics.vela`](../../examples/generics.vela)。

## 3. 声明与类型应用

### 3.1 语法和身份

```text
TypeParameters := '<' TypeParameter (',' TypeParameter)* '>'
TypeParameter  := Identifier ('extends' Type)?
```

顶层函数、class、interface、透明类型别名、class 的实例/静态方法以及 interface 方法均可声明类型参数。构造函数使用 class 的类型参数，不另外声明构造函数类型参数。普通类型应用仍写作 `Box<int>`，类型标注不提供 raw type 或部分省略实参语法。调用和有完整函数上下文的函数值允许整体省略类型实参，显式书写时必须提供完整列表。

```vela
interface Reader<T> { read(): T; }
interface Mapper { map<T, U>(value: T, operation: (T) => U): U; }
class Box<T> {
  value: T;
  transform<U>(operation: (T) => U): U { return operation(this.value); }
}
type ReaderValues<T extends Reader<int>> = T[];
func read<T extends Reader<int>>(reader: T): int { return reader.read(); }
```

同一参数列表中的名字先全部登记，再解析上界；上界可以引用后面的参数。参数以所属声明和序号标识，同名但不同作用域的参数不是同一类型。重复参数名报错；跨作用域遮蔽按现有词法规则解析，不靠字符串替换区分所有者参数和方法参数。模块限定名和透明别名按正常类型解析处理。

### 3.2 上界的类型和可空性

显式上界可以使用既有静态值类型，包括基本类型、枚举、class、interface、数组、函数、已有泛型实例、其可空形式，以及作用域内的类型参数。上界的类型应用本身也必须满足相应声明的约束。精确基本类型或不变容器上界只允许已有静态关系能证明的类型，不产生数值提升、结构化实现或容器协变。

`void`、null 字面量类型和 `dynamic` 不能作为显式上界。前两者不能描述普通值能力；dynamic 不提供静态约束证明，需要无约束参数时省略 `extends`。无上界参数不隐式变成 dynamic，也不获得任意成员；它的实际类型可以是现有允许的值类型，包括可空类型及显式 dynamic。现有仅返回值等位置允许的 void 类型实参继续按每个真实使用位置检查，不能进入字段、参数、数组元素或受约束值位置。

非空上界拒绝可空实际类型。可空上界允许符合其非空部分的类型及其可空形式，读取成员前仍须完成现有非空检查。`T?` 对类型参数应用可空化；具体化为已有可空类型时不会产生第二层可空包装。null 本身不独立确定一个缺失类型实参，普通 null 证据与其它证据的合并沿用现有可空推导规则。

### 3.3 递归约束

`T extends Comparable<T>` 是合法自引用：约束说明 T 与某个参数化类型之间的关系，不要求构造无限嵌套的具体类型。参数之间也可以通过参数化上界形成相互依赖。

只包含类型参数转发和可空包装、没有实际类型构造的直接或间接循环非法，例如 `T extends T`、`T extends U, U extends T`。透明别名先按身份展开后判断；别名不能隐藏循环。合法递归不代表任意具体实参都满足约束，实际类型应用仍必须证明所有替换后的关系。

约束图和子类型查询按参数身份及规范类型节点处理，使用有明确递归语义的工作队列和查询记忆；不能遇到重复查询就无条件认为约束成立。现有类型嵌套和泛型展开深度限制继续约束真实展开，不能用放宽约束、改成 dynamic 或无限生成特化来终止递归。

## 4. 静态关系与定义检查

### 4.1 约束满足不是动态可转换

用 `A <: B` 表示静态可证明的类型关系。它依据类型身份、现有可空关系、class 继承和显式 implements 的传递关系，以及已有类型构造的规则判断。名义类型身份包含定义模块、声明身份和规范类型实参；不能仅凭成员同名认为实现了 interface。

例如 `Derived<int> extends Base<int>` 可以证明前者属于后者；这不允许 `Base<int>` 变成 `Base<dynamic>`。类型参数 P 的已声明上界可用于证明 P 的能力；相同参数始终保持其身份，不把所有上界相同的参数视为相同类型。静态关系同时服务于约束检查和相应普通赋值/传参，不能让约束证明允许一次上转型而实际参数绑定拒绝同一关系。

受约束参数不能用 dynamic 类型实参直接通过证明。dynamic 表达式进入已确定的具体参数类型时，仍经过现有受检查转换和诊断策略；调用者可以先用 `is` / `as` 建立具体类型，再参与泛型推导。不能把 `CanAssign` 对 dynamic 的接受分支当成上界证明，也不能将运行时当前值的种类当作编译期类型实参。

### 4.2 未实例化的定义也必须正确

编译入口加载的每个模块中的泛型定义都在抽象类型参数环境下检查，包括未调用的泛型函数、未构造的 class、接口签名和透明别名。上界决定成员可见性、调用签名及可证明的类型关系；字段、局部、返回值、闭包、async 和控制流规则使用同一个类型检查器。

```vela
func readValue<T extends Reader<int>>(value: T): int {
  return value.read();
}

// 非法：Reader<int> 不一定是调用者选定的具体 T。
func replace<T extends Reader<int>>(value: T, other: Reader<int>): T {
  return other;
}
```

无上界的 `T` 可传递、存储于合法的参数化类型、捕获及返回；需要使用特定成员、操作符或构造能力时，必须有能证明该能力的上界，或显式传入普通函数值。不能因为当前某个实例化恰好拥有成员就接受未声明能力。此规则替代仅在具体化时碰巧成功的模板路径，不保留两种相互冲突的泛型体语义。

上界不是构造能力，`T extends Base` 不允许 `T()`；需要构造时传入 `() => T`。interface 的具体泛型应用、普通方法和泛型方法实现均须匹配声明。泛型 override 的参数数量、规范化上界和方法类型签名在参数重命名后等价，不能缩紧调用者已经获得的契约；不借此新增一般方法重写变型规则。

类型别名先验证自己的参数和上界，再展开目标；目标类型应用也须对所有合法参数成立。例如 `Bounded<T extends Reader<int>>` 的别名不能写成无约束的 `type Alias<T> = Bounded<T>`，也不能因透明展开删除一次约束验证。别名不创建新的运行时名义类型。

## 5. 统一推导与显式实参

显式类型实参固定该参数，不允许推导改写。省略实参时，实参、预期类型、回调签名和声明上界进入同一个约束域。普通 API、SDK intrinsic、class/Set/Map/Future 等构造、方法、别名和泛型函数值继续使用统一求解器；不为上界建立第二套推导入口。

推导保存静态关系、相等条件和证据来源，不仅逐个参数选择第一个见到的类型。不变类型构造按相同构造及对应实参相等关系分解；普通函数类型沿用现有签名契约。上界通过真实名义父类型投影提供证据：若 `T extends Reader<E>`，而已知具体 T 实现 `Reader<int>`，可以推导 E 为 int。不能把相似成员或类型名称文本解析成这种关系。

```vela
func readItem<T extends Reader<E>, E>(source: T): E {
  return source.read();
}
```

其中 E 可以由 T 的真实 Reader 实现推导。若多个名义路径给出冲突的实参，声明或调用必须报错，不按遍历顺序选择一个实现。

F-bound 求解不能固定为“先猜 T，再单独检查上界”。例如 `B extends A<B>`、`C extends B`，而函数要求 `X extends A<X>`：实参 C 的类型可通过明确的继承路径约束 X 为 B；不能只试 X 为 C 后立即失败。这种选择必须由声明上界和真实名义路径证明，不扩展为任意寻找共同业务父类型。对没有相关声明上界的普通推导，现有严格同类型及可空合并规则继续有效。

求解器传播参数依赖、名义投影和上下文直到稳定，再验证所有替换后的上界及最终实参赋值关系。候选必须在现有类型关系下具有唯一可确定的最具体解；没有解或存在不可比较的有效候选时产生诊断。不能任选一个上界、父类型、dynamic 或实现路径消除歧义。

没有实参或上下文证据的类型参数不会仅凭声明上界获得默认值。例如 `func empty<T extends Reader<int>>(): T[] { return []; }` 的无上下文 `empty()` 仍报类型实参不足；`empty<ConcreteReader>()` 或完整目标类型可以提供证据。`const values = Map()` 继续报错。本规则与 Dart 的默认上界实例化有意不同。

依赖上下文的 lambda、泛型函数值、空构造及嵌套调用仍延迟到相关类型足够确定后检查。延迟保留源码位置的流分析事实，不能重复运行用户表达式、改变求值顺序，或丢失已经发生的潜在赋值/调用效果。返回上下文只提供约束，不能使不匹配的最终实参合法。

## 6. 方法、函数值与接口分派

泛型方法的所有者实参与方法实参具有不同身份。实例方法先由接收者确定所有者实参，再求解方法实参；静态方法按现有所有者类型绑定规则处理。捕获接收者的方法值使用同一具体应用与现有闭包布局，不产生第二套方法泛型规则。

给定普通函数上下文时，泛型函数或方法具体化为一个签名：

```vela
func identity<T>(value: T): T { return value; }
const operation: (int) => int = identity;
```

没有足够上下文时不能把未求解模板当成运行时函数值。函数类型保持现有 `(T) => U` 形式，不新增携带开放类型参数的函数类型。需要对同一逻辑使用不同类型时，在各静态使用点生成对应具体应用。

`interface Service<T>` 的具体应用保留接口名义身份及实参；实现 class 必须显式声明匹配的应用。同一 class 经直接 implements 或继承路径获得同一泛型接口的不同实参时，在 class 定义处报错，不能等到某次推导才选择一个应用。接口方法自身的类型实参在每个静态调用点确定。该调用所需的具体方法签名及所有可达实现，在进入后端前由同一语义生产者建立；lowerer 和原生发射器不重新寻找实现或推导实参。

接口分派键必须区分接口声明、所有者实参、方法声明及方法实参，并接入既有 interface 调用和可达性机制。具体选择器沿现有绑定阶段生成，不从特化名称反向解析。相同应用复用选择器；不同应用不能混用代码、字段布局或返回类型。封闭 AOT 和可重载 JIT 的调用行为一致。

动态接收者不提供足以求解开放泛型方法的声明。调用这种方法前需要 `is` / `as` 得到已知 class/interface 接收者类型；不增加按运行时值生成泛型实例或退回解释器重试的路径。现有非泛型 dynamic 调用保留其正常边界。

## 7. 编译器、执行和持久化契约

### 7.1 前端事实与具体特化

类型参数节点是唯一的语法来源，模块绑定、AST 克隆、别名展开、定义检查、特化、初始化/捕获分析和语义索引均遍历它的上界。模板及其声明来源保留身份和规范化约束，不靠多份名字列表同步语义。

语义模型区分抽象参数、规范类型应用和具体执行类型，记录定义检查结果、名义投影、已验证实参、成员/方法身份及必要的受检查转换。定义检查和实例化使用同一套静态关系。不能把类型参数塞进现有字符串类型名，再让消费者从文本猜测参数身份或上界。

Specializer 消费已确定的应用，负责替换、规范化和唯一化具体声明；不决定约束满足关系。补齐 interface 和方法的模板及应用路径，删除与新参数节点冲突的旧字符串参数语义。显式和推断实参、透明别名及导入别名的等价应用复用同一特化，不把源码参数名字作为特化身份。

### 7.2 IR、JIT、AOT 与宿主

执行 IR 只接收具体类型、布局、调用签名及目标。抽象参数、上界和推导变量不进入寄存器、字段存储或机器调用约定；为重载和工具保留的声明元数据与执行类型明确区分。基本类型继续使用既有紧凑存储，不因泛型声明检查而统一装箱。

泛型约束不需要运行时泛型求解器。类型测试、显式转换、接口分派、异常、GC 根和 async 恢复复用现有操作；泛型接口/方法带来的具体调用与类型布局仍须接通原生映像与缓存、运行时元数据、公共效果分析、原生发射及可达性。不能以“前端功能”为由跳过实际改变的下游契约。

原生宿主仍注册具体 C++ 签名。脚本泛型可调用这些签名，但不能导出一个由宿主在运行时任意选择类型实参的开放泛型符号。AOT 导出和独立发行只携带所需的具体应用；缺少可达实现必须在发布前诊断，不在首次调用时补编译或动态选择执行后端。

### 7.3 缓存、重载与工具

模块公开声明和保留特化记录参数身份、规范化上界及引用的名义声明。缓存键和依赖指纹覆盖这些事实；实际持久化布局变化时更新相应格式版本和构建身份。旧格式不能通过忽略上界继续加载，单纯参数重命名或导入前缀变化不应形成不同的语义身份。

类型参数数量、语义上界或泛型接口方法契约变化按声明结构变化处理，Hot Reload 要求 Reload；等价的参数重命名不属于契约变化。Reload 按现有新 Isolate/重新初始化流程重建应用。普通实现体更新沿用现有版本与代码退休协议，旧帧、闭包、挂起续延和去优化记录使用其所属版本的具体签名，不重解释旧类型实参。

LSP 在未调用的泛型定义中也能提供参数身份、上界成员补全、悬停及跳转。重命名区分类型参数、同名其它作用域参数和上界引用。格式化、文档生成、语义 token、编辑器高亮和 REPL 完整处理嵌套泛型及错误恢复；尚未完成的输入不能清空已确定事实。中英文用户文档与示例在功能实现完成时同步更新。

## 8. 诊断与验证矩阵

诊断关联类型参数、上界或具体应用的真实源范围，说明实际类型、要求的上界和失败的参数/投影；模板内部错误同时保留定义位置，具体应用错误可附调用来源。不能只暴露生成的特化名称或最终 lowerer 错误。

| 分类 | 必须覆盖的情况 |
| --- | --- |
| 声明 | 重复参数、限定上界、前向参数引用、跨作用域同名、非法上界、未使用但错误的泛型定义 |
| 递归 | 合法 F-bound 和互相依赖、直接/间接无信息循环、别名隐藏循环、真实展开深度超限 |
| 静态关系 | class 继承、显式接口实现、泛型父类型投影、不变容器、可空参数、dynamic 不能作约束证明 |
| 定义检查 | 上界成员可读、未声明成员非法、T 不等于上界、无上界参数、构造需工厂、void 的合法和非法位置 |
| 推导 | 显式/推断等价、从上界提取其它参数、F-bound 经父类型求解、上下文和回调、无解/歧义、没有默认类型实参 |
| 泛型使用 | class、interface、函数、实例/静态方法、接口泛型方法、透明别名、方法值和跨模块限定名 |
| 接口契约 | 不同具体应用、泛型 override 等价、实现遗漏或缩紧约束、所有可达实现、动态接收者的静态要求 |
| 执行 | 封闭 AOT、JIT 初始/优化层的等价结果与错误；闭包、GC、异常、async 和去优化中的具体类型 |
| 持久化与工具 | 缓存恢复、独立原生分发、保留特化、上界变更的 Reload、alpha 等价、LSP/格式化/REPL |

还需回归现有无约束泛型、数组高阶方法、Future/Set/Map intrinsic、原生绑定和非泛型调用。定义检查不得靠执行初始化器或用户函数取得类型信息；验证延迟检查不会重复源码副作用。

## 9. 实施阶段与完成条件

| 阶段 | 生产路径 | 完成条件 |
| --- | --- | --- |
| G0：声明与身份 | 参数节点、上界语法、泛型接口/方法、模块绑定、克隆、声明来源 | 所有声明位置保留同一参数身份和类型引用；非法或未完整声明产生诊断 |
| G1：静态契约 | 抽象参数、名义关系、可空/动态边界、递归约束、定义检查 | 未实例化的定义也正确；所有实际静态证明与普通参数绑定一致 |
| G2：统一推导 | 上下文、回调、名义投影、参数依赖、F-bound、别名/函数值 | 求解器统一产生唯一可验证实参；信息不足和冲突不降级 |
| G3：具体交付 | interface/方法特化、具体选择器、IR、JIT、AOT、宿主边界 | 每个调用及可达实现接通所有执行配置，无开放参数进入执行类型 |
| G4：状态与工具 | 缓存、镜像、保留特化、Hot Reload/Reload、LSP、格式化、REPL | 契约变化不能复用不合法旧应用，工具准确反映未实例化定义 |
| G5：发布验证 | 全部正确性矩阵、中英文契约、源码/宿主语料、独立发行、Release 基准 | 完整回归及静态检查通过，冲突的旧参数和模板路径删除 |

全部阶段共同构成本设计的完成范围。不能以 parser 接受 `extends`、只检查显式实参、一个泛型函数测试通过或单个后端成功作为完成。

Release 基准保留无上界泛型和等价手写具体实现作对照，测量定义检查与推导时间、特化数量、峰值内存、生成代码体积及执行耗时。重复名义投影和递归约束不能导致无界重复检查或指数式候选展开；查询以声明/类型身份索引并复用结果。运行性能与前端成本分开报告，不以编译成功声称零开销。
