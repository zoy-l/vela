# Bytecode images and compilation cache

[**English**](compilation_cache.md) | [简体中文](../zh-CN/compilation_cache.md)


`vela compile source.vela output.vbc` writes a bytecode image without running it.
`vela exec output.vbc` loads and validates the image, then runs `main` with the same
exit and diagnostic rules as `run`. The input source files are not required to
execute the image. Source paths and PC mappings remain available for stack traces.

`vela run source.vela` uses `.cache/vela` relative to its working directory.
The embedding API `CompileFileCached(path, cache_directory, isolate)` exposes
`Hit`, `Absent`, `Stale`, and `Invalid` results. `CompileFile` remains the explicit
uncached compilation API. No global cache directory or environment changes are used.

## Identity and invalidation

Cache keys use the absolute, normalized requested entry path. The cache stores:

- A SHA-256 build identity over compiler, runtime, VM, base, build configuration,
  target OS/CPU, pinned dependency declarations, and the Unicode casing generator
  and input manifest, plus third-party GN configuration, generated by `vl config`.
- XXH3-128 content fingerprints of every source consumed by
  the actual module loader, including referenced default standard declarations.
- Every requested source path and its canonical identity, so symlink retargeting
  invalidates the result even when the old target remains unchanged.

Modification times and file sizes never establish a cache hit. A hit reads and
hashes dependencies and checks canonical paths, then loads the validated image;
it skips lexing, parsing, type checking, specialization, IR and encoding.
Unsaved editor overlays use the ordinary module checker rather than the disk cache.

The cache container has a separate checksum covering metadata and bytecode.
Its `VELACCH2` schema stores only source fingerprints and file resolutions.
Stale or damaged entries are rebuilt from source. Failed compilation does not
replace a previously valid entry. Missing native symbols or changed signatures
prevent image loading; rebuilding performs the normal native binding diagnostics.
I/O failures are explicit API errors; the CLI exits with sysexits `74`.

Writes use a uniquely named file in the destination directory followed by an
atomic replacement through the platform publication primitive described below. A failed write
does not damage the previous entry. Competing writers publish whole images.
This guarantees atomic visibility, not crash durability of all directory metadata.

## Image format and ownership

Version 9 starts with `VELABC01`, a little-endian uint32 version and an XXH3-128
payload checksum. Counts, text lengths and graph identities use uint64. No raw
pointers, native C++ object layouts, heap snapshots or runtime global state are
serialized. Integers preserve all 64 bits; doubles preserve their bit patterns.

The payload contains class/array/collection graph definitions, shared layout
tables, rooted string pools, source path pools, functions, handlers, source
mappings, native names and exact signatures, and global initializer IDs.
Function records retain the async flag. Class records distinguish ordinary
classes, standard Error, and standard DateParts. Loading validates standard
shapes and binds them to the receiving Isolate's canonical layouts; DateParts
has seven non-reference int fields. Date.toUTC builtin wrappers retain the
checked class-pool operand. Numeric parsing and casing builtin IDs use the
same validated instruction path.
ByteArray and ByteData have separate object-kind constraints in array,
collection, and runtime type metadata. Byte builtins validate their argument
windows through the shared arity table. Owners, views and backing bytes are
created during execution; their runtime pointers are never serialized.
RegExp and RegExpMatch retain distinct object-kind constraints. RegExp array
results carry compiled array-layout pool operands, checked by the VM against
the expected match/string/nullability shape. Engine code and match spans are
created during execution and are never image payloads.

Dynamic metadata includes nominal enum and interface identities, structural
function and Expected signatures, Future/Completer payload signatures, and public
member dispatch records. Function call records retain parameter names, optional
and rest flags, checked type indices, and result types. Loading validates these
contracts and Expected GC layouts before publishing executable code.

Array/collection/signature graph reconstruction uses an iterative topological traversal;
cycles and missing references are diagnosed. Counts are bounded by the remaining
input before allocation. `Program::Create` validates code and cross-function
targets after reconstruction and before any execution.

Loading binds native symbols from the receiving isolate and creates fresh
layouts, roots and lazy global state. The image bytes and source isolate can be
destroyed after loading. The receiving isolate must outlive the loaded program
and its handles, just as for a freshly compiled program.

Images are trusted compiler artifacts with corruption detection. The checksum
does not authenticate a producer, and the bytecode verifier is not a security
sandbox or a replacement for host trust policy. Version changes are rejected;
there is no legacy image loader.

## Validation and platform contracts

GoogleTest covers fresh-isolate ownership, GC stress, closures, interfaces,
generics, collections, exceptions, int/double/string pools, all truncations,
checksums, structurally invalid checksummed payloads, native signature changes,
source invalidation and Unicode paths. File tests cover empty files,
replacement failures, concurrent writers and readers that retain an old snapshot.
Windows publication uses `SetFileInformationByHandle(FileRenameInfoEx)` with
replace/POSIX semantics; concurrent replacement cannot leave the destination in
the delete-pending race observed with `MoveFileExW`. Other platforms use atomic
same-directory rename. No retry loop or delete-then-write path is used.
Vela's Windows readers open with `FILE_SHARE_DELETE`, retaining a complete old
snapshot while a replacement becomes visible. Handles opened by other software
without deletion sharing can still block replacement. The Win32 rename buffer
includes its terminating UTF-16 zero even though `FileNameLength` excludes it;
tests cover every filename alignment and concurrent snapshot reads.
See Microsoft's [rename flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information).
